### Server / API code

- [ ] **[SCALE-5 + SCALE-6] Nudge cron is O(users) serial and silently truncates** — evaluation is ~10–15 serial Supabase round-trips + a serial Expo push per user in one request, and five queries cap with **no `ORDER BY`**, so when a cap is crossed the dropped users are arbitrary and nothing errors. **Not biting yet — measured 2026-08-18:** `streak_state` 399/1000, `nudge_schedule` 251/1000, `trips` **1,242/2,000 (62%)**, `notify_streak` profiles **2,570/5,000 (51%)**; the `nudge_log` attribution sweep (`nudges.ts:628`, limit 1000) reads a 2-hour window and is nowhere near. The two at ~half capacity are the ones to fix before they cross — adding `ORDER BY` + pagination is far cheaper than diagnosing silently-skipped users later.
- [ ] **[SCALE-12] Append-only tables have no retention — but they are nowhere near mattering** — `services/mobile-api/src/routes/retention.ts` covers only `truncate_old_gps_trails`, `flag_inactive_users`, `select_purgeable_inactive_users`. Measured 2026-08-18: `notification_log` **14,274** rows, `activity_feed` **629**, `xp_events` **1,502** — trivial. The whole `public` schema is **50 GB**, essentially all `road_risk_data` (67.9M rows), so the real ceiling is the Supabase tier (SCALE-20), not these logs. **The finding also names `rider_xp_log`, which does not exist** — the table is `xp_events` (same doc-vs-reality drift class as error-log #78; `.claude/CLAUDE.md` repeats the wrong name). Deprioritised: fix the table name in the docs, revisit retention when a table reaches ~1M rows.
- [ ] **[SCALE-18] Expo delivery-receipt polling is implemented but never called** — `services/mobile-api/src/lib/push.ts:152-195` exports the receipt poller with a correct dead-token classifier, and **no caller exists anywhere in the codebase** (verified 2026-08-17). Only the immediate in-ticket `DeviceNotRegistered` signal is pruned (`notifications.ts`), so tokens that die *after* the ticket is issued linger and drag sender reputation. 691 users hold tokens as of 2026-08-18. Needs a ticket_id→token store (both `notification_log` and `nudge_log` keep `expo_ticket_id` but neither keeps the token) + a cron ~30 min after send.
- [ ] **[PERF-3 / SCALE-14] `GET /v1/trips/history` ships full GPS trails for a list view** — `services/mobile-api/src/lib/submissions.ts:387` still selects `gps_trail` for every row (verified 2026-08-17). Egress + parse cost scale with ride count. Deferred once as June-B6 because `TripCard` uses the trail on expand and as a distance fallback — the fix needs a summary/detail split, not just a column drop.
- [ ] **[SCALE-9] `get_city_heartbeat` has no server-side caching** — 6 spatial aggregations per view, two unbounded over all-time `trip_shares`; no cache/TTL anywhere in `services/mobile-api/src/routes/feed.ts` (verified 2026-08-17).
- [ ] **[SCALE-10] `get_neighborhood_leaderboard` ranks the entire qualifying set before slicing** — `supabase/migrations/202604140001_leaderboard.sql:200` `ROW_NUMBER() OVER (ORDER BY …)` over all rows, then top-50 (verified 2026-08-17); settlement runs globally.
- [ ] **[SCALE-2] Every authenticated request makes a GoTrue HTTP round-trip** — `services/mobile-api/src/lib/auth.ts:83` `supabaseAuthClient.auth.getUser(accessToken)` per request (verified 2026-08-17). Local JWT verification against the project JWKS would remove a network hop from every call.
