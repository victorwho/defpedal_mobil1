# Error Prevention Rule

Before making any code changes, consult `.claude/error-log.md` for known pitfalls.

## Pre-change checklist

1. **Adding imports?** Verify the symbol exists in the target module and is exported (Error #1)
2. **Using native modules?** Use lazy `require()` not top-level `import *` (Error #2)
3. **Installing APK?** Debug vs release — check with dev menu test after install (Error #3)
4. **Building native?** Use short path `C:\dev\defpedal` or `C:\dpb` (Error #4)
5. **Adding store fields?** Clear app data after schema changes (Error #7)
6. **Adding Mapbox layers?** Use filter-based hiding, not conditional mount/unmount (Error #12)
7. **Using emoji in Mapbox?** Plain text only on Android (Error #13)
8. **Fetching POI data?** Prefer Mapbox vector tiles over Overpass API (Error #14)
9. **Using SafeAreaView?** Import from `react-native-safe-area-context`, not `react-native` (Error #15)
10. **Phone blank?** Check USB + port forwarding + Metro status first (Error #16, #17)
11. **Changed icons/manifest/res?** Build script syncs `android/app/src/` automatically, but verify with a preview build — dev and release use different source dirs (Error #20b)
12. **Detecting Expo native modules?** Use `requireOptionalNativeModule()` from `expo-modules-core`, NOT `NativeModules` from React Native (Error #21b)
13. **Installing Expo native packages?** Must be in `apps/mobile/package.json`, not just root — autolinking only reads the workspace (Error #22b)
14. **Using community native modules (non-Expo)?** Check `NativeModules.<BridgeName>` BEFORE `require()` — the module's invariant throw can escape try/catch (Error #23b). Closely related: **TurboModule property access** (e.g. `mod.GoogleSignin`) fires `TurboModuleRegistry.getEnforcing` LAZILY, so wrapping only the `require()` line in try/catch leaks the invariant on the next-line destructure. Pull the destructure INSIDE the same try (Error #45)
15. **Adding `// eslint-disable-next-line some-rule`?** Confirm the rule is actually registered first by running `npx eslint <the-file>`. This repo does NOT ship `eslint-plugin-react-hooks`, so disables for `react-hooks/exhaustive-deps` and `react-hooks/rules-of-hooks` will themselves error and fail CI's lint-ratchet (Error #35)
16. **Adding a new Postgres SELECT?** Don't trust columns named in nearby/legacy code — verify they actually exist in the live schema with `SELECT column_name FROM information_schema.columns WHERE table_schema='public' AND table_name='X'` before depending on them. Especially "denormalized aggregate" columns on `profiles` (`total_rides`, `last_ride_at`, `streak_count`) — these are convenience fields maintained by triggers/cron and may have been removed without dropping the column, or planned but never added (Error #39)
17. **Local CI parity?** Pre-push hook only runs typecheck + lint, NOT the security audit. CI's Security audit step runs **`npm run audit:ci`** (`scripts/audit-ci.mjs`) — it audits only PRODUCTION (shipped) deps and fails on any high/critical EXCEPT a small **documented allowlist** (in that script) of advisories living in transitive dev/build/telemetry tooling that npm misclassifies as production but which is not shipped (e.g. `ws` via Expo/Metro dev-server `GHSA-96hv-2xvq-fx4p`; `protobufjs` via posthog→@opentelemetry `GHSA-wcpc-wj8m-hjx6`; `undici` via @sentry/react-native→@sentry/cli build-time source-map tool `GHSA-vxpw-j846-p89q`, added 2026-06-25). It replaced bare `npm audit --omit=dev --audit-level=high` on 2026-06-18 because npm `overrides` silently refuse to rewrite those deeply-nested workspace sub-trees in npm 11 and `npm audit fix` removes `@opentelemetry/core` (breaking `@sentry/node` — 12 mobile-api suites fail). (Earlier history: before 2026-06-09 CI ran without `--omit=dev` and failed on the dev-only vitest GHSA-5xrq-8626-4rwp critical, which is why `--omit=dev` was added.) Run `npm run audit:ci` locally to mirror CI; run plain `npm audit` to also review dev-tool advisories. **Before adding an allowlist entry**, confirm the advisory genuinely cannot reach shipped code and document why; re-review on every dependency bump. Prefer `npm audit fix` (non-breaking) / a dependency bump when one is actually available
18. **Adding a PNG-bearing token file that's covered by a test?** Use ES `import logo from './x.png'` rather than `require('./x.png')`. Vitest can't follow `require()` to a binary at runtime, but Vite's bundler resolves ES imports cleanly. Add `*.png` (and `*.jpg`/`*.svg` if relevant) module declarations to a workspace `.d.ts` so tsc accepts the import. Metro is happy with either form so the runtime path is unchanged (Error #42)

19. **Reasoning about risk-score / road-data coverage?** Don't trust this repo's docs — `road_risk_data` is produced and swapped by the separate `C:\dev\OSRM_Server` project, whose CLAUDE.md is the source of truth for generation, row count and countries. This repo described the RO+ES state for 12 days after the EU-wide swap, which caused a whole UI review to be written on a false premise while the app silently withheld risk features from 29 countries that had live data. Verify against the live DB before deciding whether a feature ships (Error #78)
20. **Adding a per-country feature gate?** Put it in ONE exported predicate in `packages/core/src/countryCoverage.ts` (`isRiskDataAvailable`, `isHeatRoutingAvailable`, `isRouteSupported`) — never a function-local const at the call site. The safe-vs-fast comparison gate was a private `COMPARISON_ELIGIBLE_COUNTRIES` inside `mapbox-routing.ts`: invisible to every other surface, un-greppable by feature, and it outlived the data limitation it encoded by 12 days (Error #78)
21. **Deleting or moving a doc?** `git grep -F "<filename>"` first — this repo names docs from *code*: `build.gradle` prints `mobile_release_runbook.md` in a signing error, `TODO.md` links into `changestoimplement.md` by line number, and `sentryfix.md` is cited from `ci.yml` + `app.config.ts` comments. Finished one-off docs live in `docs/archive/` (see its README for what moved and what replaced it)
22. **Writing a PostGIS "nearest feature" lookup?** Probe with a POINT on the geometry (`ST_LineInterpolatePoint(seg, 0.5)`), never the line itself — line-to-line distance collapses to **0** at every shared node, so at an intersection every crossing road ties and `order by ST_Distance(...) limit 1` becomes a coin flip. `get_segmented_risk_route` shipped this way from the first risk release: 56–79% of route segments had ties with an average 21–31 point score spread, silently mispainting the map in both directions. Check the tie population before trusting `limit 1`, order with `<->`, and read *actual* `EXPLAIN ANALYZE` time rather than `cost` before believing a "big table = slow" claim (Error #79)
23. **Syncing device-local state to the server?** Decide per field who owns it, and write it down. If the server *enforces* the setting (quiet hours gate every push; notify flags gate categories), the server owns it — a client may seed it when the server has no value, never overwrite it on mount. The Profile screen pushed the device-scoped Zustand defaults unconditionally, so a reinstall reset a rider's quiet-hours window and silently re-opted them into sharing they had turned off. Ask: **what does this push when the local store is empty?** A write-only "sync" looks identical to a working one until someone reinstalls (Error #81)
24. **Writing or touching a cron?** Two things. (1) Count **round-trips per item**, not queries — Supabase is in `us-east-1` and Cloud Run in `europe-central2`, so each is ~100 ms; ~6 per user across 687 users is ~410 s and the Cloud Scheduler attempt deadline is 300 s. Batch with chunked `in (...)` loads (`loadFirstRideLogIndex` / `loadRiderTripFacts` are the pattern). (2) A cron that times out is **truncated, not just slow**, and without a cursor it re-grinds the same prefix every run so the tail is never processed — silently, because the job still writes rows before dying. `mia-notification-cron` did exactly this daily for 8+ days (Error #82)
25. **Shipping code that reads/writes a NEW column, table or RPC?** Verify it exists **in the live DB** before you deploy — `select column_name from information_schema.columns where table_name='X'`. A migration file in `supabase/migrations/` proves nothing: this repo cannot run `supabase db push` (history diverged), so migrations are applied by hand and deployment knows nothing about schema. `saved_routes.avoid_heat` shipped in the SAME commit as its migration and still broke every save for a week (Error #83b). When a commit carries several migrations, assume partial application and check each one
26. **Adding a column DEFAULT, or relying on a BEFORE-INSERT trigger to fill a column?** They are mutually exclusive — Postgres applies column defaults **before** BEFORE-INSERT triggers, so a trigger guarded on `IF NEW.col IS NULL` never fires once the column has a default. `hazards.expires_at` had both from day one, which meant every per-type TTL in `hazard_baseline_ttl()` was dead code for the app's entire history: potholes expired in 24 h instead of 14 days, silently, through two later migrations that *edited* that function. Assert the derived value (`expires_at - created_at`), not just that the insert succeeded (Error #91)
27. **Backing an `ON CONFLICT` upsert with a unique index?** Do not make it partial. Postgres only uses a partial unique index for conflict inference when the statement carries a matching `WHERE` predicate, and PostgREST does not emit one — every upsert fails with *"no unique or exclusion constraint matching the ON CONFLICT specification"*. Unique indexes are `NULLS DISTINCT` by default, which already gives you the "don't constrain the NULL rows" behaviour a partial index was reaching for (Error #92)
28. **Passing a filter parameter to a third-party API?** A 200 is not proof it was applied. Cologne's Open311 accepts `?service_request_id=a,b,c` and silently ignores it, returning the 100 most-recent rows instead — which made status-sync a no-op that still reported a healthy `statusChecked: 100`. Verify a filter by asking for something you can prove the response should NOT contain, count the **matches** rather than the rows received, and prefer the spec's addressable single-resource endpoint when correctness matters (Error #93)
29. **Writing a "source looks dead" detector?** Use elapsed time, not consecutive empty runs. A cursor that advances its window to `now` makes any run shortly after a completed one legitimately return zero — so a run-count rule pages on a healthy pipeline, and an alarm that fires on healthy behaviour gets muted along with the real one. Track `last_items_at` and escalate past a threshold instead. Test detectors by exercising the *healthy* path repeatedly, not only the broken one (Error #94)
30. **Parking work in a staging table for "retry later"?** Make sure something finds it again. If the dedup check reads the same table you parked it in, the row is now invisible to the only code that could reprocess it and will stall forever — items deferred by a run budget did exactly that. Retry only reasons that are genuinely TRANSIENT; never auto-retry states that encode a human decision (low confidence, invalid value), or you re-litigate the review (Error #95)
31. **Deploying to Cloud Run?** `gcloud builds submit` uploads the **working directory**, not the commit you pushed — it has no git awareness whatsoever. Run `git fetch && git status` first and confirm `HEAD == origin/main`, nothing ahead or behind, before building; deploy from a clean tree, never a feature worktree. Two parallel sessions each deployed their own tree on 2026-08-27 and the second silently reverted the first's server code — `POST /v1/sesizari` 404'd in production while git history stayed linear and conflict-free. Note the database will NOT reveal this: migrations are applied out-of-band, so the reverted feature's tables and RPCs remain, and schema presence is not evidence the code is live. After deploying while others might be, smoke-test one route per recently-shipped feature (a missing route 404s where a live one 401s), and read the live revision with `gcloud run services describe --format='value(status.traffic[0].revisionName)'` rather than trusting a revision id quoted in a commit message (Error #96)
32. **Relying on an API token, or triaging a 403 from one?** Read the `www-authenticate` header before concluding anything — Sentry answers `insufficient_scope` there with the exact scope required, while the JSON body says only "You do not have permission to perform this action.", which is indistinguishable from an expired or revoked token. The monitoring token had every scope except `event:read`, so it returned 200 on Discover `/events/`, releases and project keys but 403 on every issue query: **"the token works" is a property of a token AND an endpoint, never of a token alone** — probe the endpoint your check actually depends on, not a cheap adjacent one. Related: a health check that can fail silently is not a control. Check #1 of the monitoring runbook is the compensating control error-log #83b names for low-volume 100% failures, and it had been dead for as long as that token was in use, because an erroring check and a clean check look identical in a transcript — run it via `npm run monitor:sentry:new-issues`, which prints which mode it used. Note Sentry scopes are **immutable on an existing token**; widening them means creating a new one, and a replacement should be a strict superset unless you have checked every consumer (this token is also the EAS build secret and is embedded in the cloud routine) (Error #97)

30. **Adding a hazard-import source?** "It speaks Open311, so it's a registry row" is false often enough to plan for. Fetch one real page first and diff its **field types** against the city that already works — Zaragoza returns `service_request_id`/`service_code` as numbers where Cologne returns strings, rejects milliseconds in `start_date` (HTTP 400 from `toISOString()`), and silently ignores `page=` in favour of a `start=` offset. None of the three fails loudly; two produce a clean zero-import. Verify a paging parameter actually **changes** the response before trusting it (Error #98, and #93 for the same trap in status-sync)
31. **Writing the message for a "this should never happen" throw?** Report what you observed and the underlying error, never a cause you did not distinguish. `"all 25 detail fetches failed — site or shape changed?"` sent a whole investigation at a third-party redesign that had not happened; the actual cause was our own unpaced 250-request burst, and the HTTP status was one line away. Also: a comment saying you are being polite to a small partner is not pacing — put it in the code (Error #99)
32. **Relying on a server-side flag to protect riders?** Name its client consumer and the version that shipped it, in the same breath. `alert_eligible=false` on geocoded imports is correct data and an **inert safeguard**: its only reader is one line in `navigation.tsx` first shipped in v0.2.129, and the fielded fleet is v0.2.123. Check the FIELDED version via Sentry release health, not the newest release commit — they routinely differ by several versions (Error #100)

## After every code change

Run `npm run check:bundle` to verify the bundle builds before testing on phone.

## Before pushing to GitHub

The pre-push hook (`.git/hooks/pre-push`) runs both `npm run typecheck` AND `npm run lint:mobile:check` — mirrors CI. The hook source of truth is `scripts/git-hooks/pre-push`; install on a fresh clone or worktree with `bash scripts/install-git-hooks.sh` (idempotent). If lint fails, either fix the new violations or run `npm run lint:baseline` from `apps/mobile/` if the regression is intentional. Never bypass with `--no-verify` (Error #35).
